### 样本暴露并修复的真 bug
1. `make_node` 对根节点（`open_meta` 无 name）抛"无效的文件目录项" → 名称缺失时用路径末段兜底。
2. `Extractor::collect_tree` 用 `child.name` 重拼路径，WIM 的 `/images/1 - 名称` 因此变成非法路径 → 改用解析器给出的 `child.path`，导出名取路径末段；同时修掉 `node_output_name` 误用 `normalize_path`（测试用恶意名 `../evil` 直接抛异常导致单测 0xc0000409）。
3. 目录时间戳还原缺 `FILE_FLAG_BACKUP_SEMANTICS` → FAT32/WIM 导出必失败。
4. 整卷导出会把 NTFS 系统文件（`$BadClus:$Bad` 等）当用户数据导出而失败 → 根目录跳过已知系统元数据文件（仍可显式提取）。

### 依赖调研结论（重要更正）
- **TSK 4.15 的 `tsk_fs_open_pool` / `tsk_fs_open_pool_decrypt` 只有头文件声明，源码与库中都没有实现**（develop 分支同样没有），CMake 能力探测失败是正确结果，不是配置问题。TSK 的 APFS 路线实际不可用。
- `TSK_FS_TYPE_XFS` 在 TSK 4.15 及官方 develop 都不存在，XFS 从未合并，不是本机构建问题。
- 方案调整：APFS 走 `libfsapfs`（20261030，支持密码解密），ReFS 走 `libfsrefs`（libyal）。
- libfsapfs 构建：缺 pkg-config（用 shim 伪造 `--atleast-pkgconfig-version`），release 包缺 `Makefile.am` 导致 automake 规则报 127（no-op shim + 把 autotools recipe 换成 `@touch $@` + 刷新生成物时间戳）。
- 本机原本无 autotools：从 repo.msys2.org 直接抓 msys 包解压成 `D:/tools/msys64`（bash 需 3.6.9 runtime，3.5.7 会 0xC0000139；根目录会被 WorkBuddy 的 PortableGit 抢占，需 `env -i PATH=/d/tools/msys64/usr/bin` 启动）。

## libfsapfs / libfsrefs 构建并接入（下午续）

**结果**：`D:/tools/libfsapfs-sdk`（libfsapfs.a 6.4 MB）与 `D:/tools/libfsrefs-sdk`（libfsrefs.a 5.0 MB）均构建成功；`ApfsFsParser`、`RefsFsParser` 已写入并接入 CMake 与工厂；两个构建 4/4 测试通过，语料矩阵 9/9 通过。

**踩坑（已写进 docs/DEPENDENCIES.md）**
- 自建 msys64 缺 `etc/fstab` → 盘符映射成 `/cygdrive/d`，configure 里 `/d/...` 全部失效；补 `none / cygdrive binary,posix=0,noacl,user 0 0` 解决。
- 工具包不带 `msys-*.dll`：真正的 DLL 在 `lib*` 包（`gmp`/`mpfr`/`libreadline`/`zlib`/`libpcre`/`liblzma`/`libzstd`/`libbz2`/`gcc-libs`）。缺 `msys-pcre-1.dll` 时表现为 configure 报 "no acceptable grep could be found"。
- 必须用 msys 的 `make`；`mingw32-make` 是原生程序，无法 stat `/d/...`，报 "No rule to make target .../Makefile.am"。
- libfsapfs release 包**自带**在 Unix 上生成的 `common/config.h`（`HAVE_STRERROR_R 1`），mingw UCRT 无 `strerror_r` 声明 → 编译失败。删掉它即可（比改 include 顺序有效，因为它总能被选中）。
- 静态库要自己补 `-lz`（`.pc` 只写在 `Libs.private`）；CMake 探测也要带 `ZLIB::ZLIB`。
- libyal 不装 libbfio 头；`libfsapfs_container_open_file_io_handle` 只在 `*_HAVE_BFIO` 下声明 → UIFE 用不透明类型自行声明，并在 CMake 探测里连符号一起测，缺符号退回"仅识别"。适配层抽到 `src/drivers/fs/BfioBridge.h`（extern "C" 必须放全局作用域，否则内部链接报 used but never defined）。
- libfsrefs：`synclibs.sh` 用"tarball + 替身 git"几分钟完成（直接 clone 20 分钟只 1/16）；`autogen.sh` 必挂（autopoint 缺 gettext 骨架），改手工 aclocal-1.19/libtoolize/autoheader/autoconf/automake-1.19，另需从 libfsapfs 借 `po/Makefile.in.in` 与 `config.rpath`；`make` 最后在 `po` 停下，用 `make -C include install` + `make -C libfsrefs install` 绕过。

**能力结论（重要，别夸大）**
- libfsrefs **没有**读取文件内容的接口，`libfsrefs_file_entry_get_size` 也只有声明无实现（nm 查不到）→ ReFS 后端只能目录+元数据，`IFSParser::can_read_content()` 默认 true、ReFS 覆写为 false，`extract`/`restore` 直接拒绝而不是产出空文件。
- libfsrefs 只支持早期 ReFS 布局：Server 2016 格式化的 1 GB ReFS 卷报 `invalid metadata block signature / unable to read ministore tree`，用其自带 `fsrefsinfo` 复现同样错误 → 不是适配层问题。语料 `raw/refs-vhd` 期望改为 `readable=true` + `list=error` 锁住该边界。
- APFS 仍无真实样本（Windows 造不出），只在"伪造 NXSB 头必须被拒绝"的负面用例上验证过。

## NTFS ACL 解码（$Secure:$SDS，傍晚）

**结果**：新增 `include/uife/drivers/fs/NtfsSecurity.h` + `src/drivers/fs/NtfsSecurity.cpp`（独立可单测），`VFSMetadata` 增加 `security/has_security`（VFSSecurityDescriptor：owner/group SID + DACL/SACL ACE）。TskFsParser 在 NTFS 挂载后惰性读 `/$Secure` 的 `$SDS` 流（≤256 MiB），按 security_id 建 map 回填节点；`list --json` 输出 `security` 对象，文本 list 追加 `[owner:S-1-... dacl:N]`。真实 VHD 验证：hello.txt owner=S-1-5-32-544、group=S-1-5-21-...-513、4 条 allow ACE 全部正确。双构建 CTest 4/4，语料 9/9。

**关键实证（与文档相反）**：$SDS 条目的 `offset` 字段 = **条目自身的流内偏移**（首条目 0），`length` = **20 字节头 + SD 的总长**（SD = data[entry+20 : entry+length)），步长 = align16(length)。linux-ntfs 文档说的 "offset 指向描述符、length 为描述符长" 在真实数据上不成立；解析器以 revision=1 + SE_SELF_RELATIVE(0x8000) 校验判别两种布局，主用实证布局、文档布局兜底。

**其他**：SID identifier authority 是 6 字节**大端**（值 5 在第 7 字节），单测初版摆错位置报 "wrong S-1-5-18"；CLI 无后端构建也编 NtfsSecurity.cpp（单测依赖）。Git Bash 调用 CLI 时 `/` 会被转成 Windows 路径——用 `MSYS_NO_PATHCONV=1` + Windows 形式镜像路径。
