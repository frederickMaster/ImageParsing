# 变异测试（fuzz）

`uife_fuzz` 把语料变异后喂给"镜像驱动 + 文件系统解析器"这条只读路径，看它会不会
崩、越界、卡死。它是 `tests/uife_tests.cpp` 里那些定点畸形用例的补充：定点用例
守的是"已知的坏形态"，这里守的是"没想到的坏形态"。

## 为什么不是 libFuzzer

`LLVMFuzzerTestOneInput` 的覆盖率反馈确实比盲变异强，但它不适合这条路径：

1. **驱动都是按路径打开的。** libewf、libtsk、libwim、libfsapfs 都只接受文件名，
   没有内存后端。libFuzzer 每次迭代都要落一次盘，绝大部分时间花在文件系统上，
   而不是解析逻辑；实测盲变异在小镜像上也只有 60–90 例/秒，覆盖率引导相对这份
   I/O 开销并不划算。
2. **Windows 上没有 clang。** 我们主要的取证使用场景是 Windows，用一套在目标
   平台上跑不起来的工具做常态回归，等于没有回归。

所以这里选"确定性变异 + 自建看门狗"：同一个 `--seed` 在任何平台复现同一批输入，
能进每次提交的 CI，也能在夜间跑满几十分钟；崩溃和超时的输入自动留档，可以直接
`--replay`。

## 一条用例覆盖什么

```
识别格式 → 打开驱动 → 按扇区读（头/中/尾）→ 扫分区 → 文件系统识别
        → 挂载 → 列根目录 → 列一级子目录 → 读第一个文件的前 64 KiB
```

导出（`Extractor`）不在里面：它会写盘，而且已经有单独的只读、深度、长路径、
资源上限用例。**异常是合法结果**——畸形输入本来就该被拒绝；只有崩溃、超时、
以及 ASan/UBSan 报告才算问题。

## 用法

```bash
# 冒烟（每次提交跑的规模，几秒钟）
./uife_fuzz --seeds build/corpus --work build/fuzz --iterations 120 --seed 20261106

# 长跑（夜间 / 本地排查，跑满 20 分钟）
./uife_fuzz --seeds build/corpus --work build/fuzz \
    --iterations 2000000 --seed 1 --seconds 1200 --case-timeout-ms 10000

# 复核一份可疑输入
./uife_fuzz --replay build/fuzz/crash/case-123456.bin
```

| 参数 | 含义 |
| --- | --- |
| `--seeds <目录>` | 递归收集语料（同一目录下的分卷兄弟文件会硬链接进用例目录） |
| `--work <目录>` | 用例、会话记录与崩溃留档的位置 |
| `--iterations <N>` | 变异用例数（默认 1000） |
| `--seed <N>` | 变异随机种子；同种子同结果 |
| `--case-timeout-ms <N>` | 单用例墙钟上限（默认 5000），超时即中止 |
| `--max-bytes <N>` | 单个输入上限（默认 16 MiB；`0` = 不截断） |
| `--seconds <N>` | 整轮时间预算（默认 0 = 不限） |
| `--selftest-hang <ms>` | 自检：故意让每个用例睡这么久，用来验证看门狗 |

退出码：`0` 跑完没发现崩溃/超时，`2` 用法错误，`3` 发现超时（输入已留档）。
崩溃（信号 / ASan 报告）会让进程直接死掉，输入仍留在 `--work` 下。

## 变异算子

| 算子 | 作用 |
| --- | --- |
| `bit-flip` | 翻 1–16 个随机位 |
| `byte-smash` | 随机覆写 1–32 字节 |
| `boundary` | 把 8 字节字段写成全 `0x00` 或全 `0xFF`（长度/偏移最容易漏的两种值） |
| `insert` / `delete` | 插入或删除最多 1 KiB（改变所有后续偏移） |
| `duplicate` | 把一段复制到另一处（重叠结构，真实损坏镜像的常见形态） |
| `truncate` | 截断到随机长度 |
| `preserve-header` | 前 4 KiB 保持原样，只打后面的元数据区 |

`preserve-header` 是必要的一半：MBR/BPB/GPT 头一改，绝大多数用例会停在"容量声明
无效"这一步，FAT 表、目录项、索引节点这些真正容易越界的地方反而一次都跑不到。
默认一半用例保留头部，挂载与读文件这两段代码才进得来（CI 语料上约 15% 的用例能
走到"挂载 + 读文件"）。

## 上哪里跑

- **每次提交**：`ctest -R uife_fuzz_smoke`，用 `scripts/gen-corpus.py --no-external-tools`
  生成确定性语料跑 120 例（固定 seed），并自检验证看门狗会掐掉卡死的用例。
  ASan 任务里同一套用例会带着 sanitizer 再跑一遍。
- **夜间**：`.github/workflows/ci.yml` 的 `fuzz-long`（每天 18:30 UTC）用 ASan 构建
  跑 20 分钟，`--seed` 取 `github.run_number`，失败时把 `crash/` 目录作为构建产物
  上传。
- **本地**：把 `--seeds` 指向真实语料目录（例如 `D:/tmp/uife-corpus`），先用默认
  16 MiB 上限跑，需要更深覆盖时加 `--max-bytes 0`。

## 已知边界

- **不是覆盖率引导的。** 能到哪段代码取决于语料和算子，算子打不到的分支永远测不到。
  语料越贴近真实证据（加密卷、多分卷、损坏样本），这个工具的收益越大。
- **导出路径不覆盖。** 需要写盘，且已有专门的只读与压力用例。
- **多分卷样本靠硬链接。** 跨卷或权限不足时退回拷贝（只拷不超过 `--max-bytes` 的
  兄弟文件），拷不了的分卷样本会因为"找不到后续分卷"提前失败，这是已知的覆盖损失。
- **超时是墙钟判定。** 判定点在看门狗轮询（100 ms 一次），所以超时预算要明显大于
  正常用例耗时，否则会误报。
