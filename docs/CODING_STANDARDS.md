# UIFE 编码规范

- **适用范围**：`include/`、`src/`、`tests/`、`scripts/` 和 CMake 构建文件
- **语言标准**：C++20
- **文档版本**：1.0
- **最后更新**：2026-11-03

本文将现有代码约定整理为后续开发的统一标准。新代码应遵循本文；修改旧代码时优先保持所在模块既有风格，避免无关的大范围格式化。

## 1. 总体原则

1. **正确性优先**：验证输入、边界和格式不变量；不猜测、不静默跳过损坏数据。
2. **默认只读**：镜像及关联分卷只能作为输入。临时文件和导出文件必须位于明确的临时/输出目录，绝不能覆盖或修改源镜像。
3. **明确失败**：不支持的变体、缺失依赖、损坏数据和元数据恢复失败都必须给出可诊断错误；不得以空结果、部分成功或默认值伪装成功。
4. **最小职责**：镜像容器驱动负责字节/扇区映射，文件系统解析器负责文件树和文件数据，VFS 负责统一路径与节点接口，CLI 负责参数和用户交互。
5. **小而可测**：优先复用已有接口、依赖和工具；避免不必要的抽象、配置项、依赖和重复解析逻辑。
6. **能力如实描述**：格式识别不等于可读取，容器可读不等于其内部文件系统可解析；文档和 CLI 必须区分“已实现”“条件支持”“仅识别”和“未支持”。

## 2. C++ 语言与格式

### 2.1 语言与类型

- 使用标准 C++20；保持 `CMAKE_CXX_EXTENSIONS OFF`，不得依赖编译器私有扩展。
- 优先使用强类型和固定宽度整数。镜像偏移、LBA、文件大小使用无符号宽类型；长度转换为 `size_t` 前必须确保范围可表示。
- 对只读参数和不修改对象状态的成员函数使用 `const`；不修改的局部变量可使用 `const`。
- 使用 `std::span` 表示非拥有的连续字节区间；使用 `std::string_view` 表示非拥有字符串视图。不得保存指向短生命周期对象的视图。
- 优先使用 `std::byte` 表示原始数据；仅在文本或流 API 需要时进行明确转换。
- 避免裸 `new`/`delete`、不必要的 C 风格转换、`reinterpret_cast` 和无依据的类型转换。指针转换仅限清晰的底层字节接口，并保证对齐、长度和生命周期安全。
- 不使用 `using namespace` 污染头文件或公共命名空间。

### 2.2 命名

遵循项目既有命名：

| 元素 | 约定 | 示例 |
|---|---|---|
| 类型、类、枚举 | `PascalCase` | `RawImageDriver`、`NodeType` |
| 函数、方法 | `snake_case` | `read_at()`、`list_dir()` |
| 局部变量、参数 | `snake_case` | `byte_offset` |
| 成员变量 | `snake_case`，私有成员名尾随 `_` | `image_size_` |
| 常量 | `snake_case`；编译期常量用 `constexpr` | `sector_size` |
| 宏 | `UPPER_SNAKE_CASE`，仅用于条件编译等必要场景 | `UIFE_WITH_LIBWIM` |

命名应表达单位、边界或含义；避免含糊缩写。协议字段缩写可在其格式语境明确时使用。

### 2.3 文件和头文件

- 头文件使用 `.h`，实现文件使用 `.cpp`。
- 头文件使用 `#pragma once`；公共类型放在匹配的 `uife` 子命名空间。
- 头文件只包含声明所必需的依赖；可前置声明时避免引入大型实现头。
- include 顺序：对应头文件、项目头文件、标准库头、第三方库/平台头；各组之间空一行。
- 平台头及可选依赖放入条件编译区域，不得让关闭可选后端的构建依赖其头文件或符号。
- 公共接口应尽量稳定、简洁；析构函数、复制/移动语义和资源所有权必须明确。

## 3. 资源、对象与错误处理

- 使用 RAII 管理文件、库句柄、锁、临时目录和其他资源；优先 `std::unique_ptr`，仅在确需共享所有权时使用 `std::shared_ptr`。
- 构造/打开流程使用候选状态：验证成功后再提交对象状态。失败时不得留下半初始化状态或污染之前有效状态。
- 使用 `std::scoped_lock` 等作用域锁；锁的生命周期应尽可能短，不在持锁时执行不必要的 I/O、回调或潜在重入操作。
- 无效调用参数使用 `std::invalid_argument`；越界访问使用 `std::out_of_range`；数据损坏、读取失败或后端错误使用有上下文的 `std::runtime_error` 或项目既有异常类型。
- 除非接口明确规定 `noexcept`，不得用宽泛 `catch (...)` 吞掉错误。若捕获异常用于清理后重抛，必须保留原始异常。
- 可恢复的非致命问题必须通过明确的结果/诊断通道报告；不得静默忽略文件系统错误码、短读或元数据写入失败。
- 错误消息应指出操作、格式/路径和失败原因；不得将敏感密码写入日志、异常文本或命令行参数。
- `noexcept` 只用于确实不会抛出的操作（例如简单状态访问/清理）；不得在 `noexcept` 函数中执行可能抛异常的工作而导致终止。

## 4. 二进制解析与只读安全

每个镜像/文件系统解析器均须遵循：

1. **边界优先**：所有读取先验证 `offset <= size`，再验证 `length <= size - offset`；避免通过 `offset + length` 检查导致整数溢出。
2. **显式字节序**：按格式规定解码字节序；对重复/双端序字段验证一致性。不得直接把不可信输入 `reinterpret_cast` 成结构体。
3. **长度与资源上限**：验证记录长度、数组数量、块大小、递归深度和累计分配大小。对大目录、连续区、链表和稀疏映射设置合理上限。
4. **映射完整性**：验证分区、extent、簇、扇区、分卷和虚拟地址到源文件偏移的映射；任何映射不完整或含糊时明确拒绝。
5. **短读错误**：若调用方要求精确读取，短读必须报告为错误；不得把未填充的缓冲区当成有效数据。
6. **不支持即拒绝**：遇到加密、压缩、增量引用、未知关键特性或需要写回的日志时，不得猜测解析或静默跳过。
7. **源只读**：源文件用只读模式打开。解析器不得对源文件执行写入、截断、修复或原地解密。
8. **关联文件安全**：自动发现分卷时限定目录和命名规则，验证卷号、总卷数、镜像 ID/UUID 等身份信息；拒绝路径逃逸、歧义和缺卷。
9. **校验失败不提交状态**：校验和、签名、几何信息或分区映射验证失败时，解析器保持未挂载/关闭状态。
10. **安全路径**：镜像内文件名进入 VFS/导出路径前须阻止路径分隔符注入、`.`/`..`、NUL 和平台不安全字符；符号链接提取不得造成输出目录逃逸。

新增限制值必须在代码中命名为常量，并在相关格式文档中说明。

## 5. 模块职责与接口

- **镜像驱动（`drivers/image`）**：打开容器、识别布局、提供只读 `read_at`/`read_sector`、报告容量与格式名。不得解析无关的文件系统目录语义。
- **文件系统解析器（`drivers/fs`）**：挂载指定范围，提供 `list_dir`、元数据和文件读取；所有访问必须限定于挂载范围。
- **工厂/注册表**：探测应当有界、只读、低成本；`supports()` 只有在对应构建启用了所需后端且解析器确实可用时才返回真。
- **VFS**：统一 POSIX 风格、UTF-8 路径和节点元数据；避免暴露后端私有对象或拥有权不明确的资源。
- **提取器**：负责输出路径安全、内容哈希、进度及可恢复元数据；不得改变源镜像。元数据恢复失败必须明确报告。
- **CLI**：验证参数后再打开镜像；错误退出码和诊断必须可用于自动化。密码只从安全输入渠道读取。

跨层行为应通过现有接口传递，不得让 CLI 直接解析某一种镜像格式或让文件系统解析器绕过镜像驱动读取源文件。

## 6. 注释、日志与用户可见文字

- 注释应解释协议陷阱、安全约束或非显然的设计原因；不要复述代码。保持简短，并随逻辑修改同步更新。
- 面向中文用户的 CLI 错误和文档使用简明中文；类、函数、变量及稳定 API 继续使用项目约定的英文标识符。
- 对格式限制，在对应驱动/解析器文档和 README 能力表中记录；公共行为变化同时更新 PRD。
- 不打印密码、密钥或证据内容。诊断只输出解决问题所需的最小信息。

## 7. 测试规范

- 每项新增格式能力至少包含：正常样本、边界/损坏样本、关键错误路径；分卷功能还应覆盖缺卷、错卷和源哈希不变。
- 优先使用可复现的合成 fixture；使用真实证据样本时不得将敏感数据或样本本身提交到仓库。
- 断言实际行为和结果：文件名、类型、大小、内容字节/哈希、元数据、明确拒绝条件和源镜像哈希。不能只测“没有崩溃”。
- 测试临时文件必须在每次运行中隔离，使用 RAII 或等效清理；测试应可并行运行，不依赖固定共享文件名。
- 测试不得依赖网络、系统挂载、管理员权限或非声明的外部工具，除非该测试明确标记为条件测试。
- 依赖可选库的测试通过 CMake 条件编译/注册；关闭后端时，其余构建和测试仍须通过。
- 修改后先运行最小相关测试，再运行对应配置的完整 CTest；涉及发布脚本时还需实际打包并检查包内文件。

## 8. CMake、脚本和跨平台代码

- 新增第三方库前先评估仓库已有依赖和平台支持；仅在清晰可选、可禁用且发现 API 能力时启用后端。
- 可选依赖用独立 `UIFE_ENABLE_*` 开关；检查所需 API，不只检查库文件是否存在。关闭后不得留下链接或头文件依赖。
- CMake 目标依赖应尽量使用 target-based 的 `target_include_directories`、`target_link_libraries` 和 `target_compile_definitions`。
- PowerShell 脚本应检查外部命令退出码、参数和目标路径；覆盖现有交付文件必须要求显式确认开关。
- 使用标准库跨平台接口优先；平台 API 放入明确的 `#ifdef` 区域并提供其他平台行为或明确的 unsupported 错误。
- 路径处理使用 `std::filesystem`；UTF-8 与 Windows 原生路径转换必须显式处理，不能假设窄字符串就是当前代码页或 UTF-8。

## 9. 提交前检查清单

- [ ] 新代码符合 C++20 与项目命名/格式约定。
- [ ] 所有不可信长度、偏移、索引、递归和分卷映射都经过验证。
- [ ] 镜像源仍只读；临时文件和输出路径范围明确。
- [ ] 失败时显式报告，不吞错、不生成成功形状的默认结果。
- [ ] RAII 管理所有资源；打开失败不会留下部分状态。
- [ ] 新增/修改了正常、错误和边界测试；相关源哈希不变测试已覆盖。
- [ ] 可选依赖启用和关闭的构建行为合理。
- [ ] README 的格式能力/限制及 PRD 状态与代码一致。
- [ ] 运行目标构建和 CTest；若改了打包逻辑，检查实际包内容。
